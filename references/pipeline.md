# 从开发文档到产品交付

当前 agent 在会话中持续推进任务，CLI 提供确定性辅助。定时或后台执行需要所在客户端的原生任务能力和用户授权。

## 1. 输入与拆片

输入：开发文档（本地路径或可访问链接）、目标仓库、交付范围及产品验收方式。先读取文档和现有实现，提取需求、接口、依赖、非功能要求及产品交付条件。有实质歧义就询问，同时推进不依赖答案的工作。

将每个需求映射到可独立验收的叶子 Issue；涉及仓库文件的切片应能独立开发、测试、评审和合并。每片写明来源文档章节、目标、验收标准、范围及必要依赖。必须共同合并的修改放一片，不按文件数或固定工期机械拆分。

较大交付创建父 Issue，子 Issue 表达可交付切片；每轮产品交付使用原生里程碑。父 Issue 写产品级验收条件和子任务覆盖表，原生父子关系与 milestone 承担组织。依赖用 blocked-by，既不要把父 Issue 当代码切片领取，也不要自动把父 Issue 的关闭等同于所有子任务完成。

```bash
ghship gh author -- issue create --title '<产品交付>' --body-file /tmp/product.md
ghship gh dispatcher -- api repos/<owner>/<repo>/milestones --method POST -f title='<阶段>'
ghship gh author -- issue create --title '<切片>' --body-file /tmp/slice.md --parent <PARENT> --milestone '<阶段>' --blocked-by <DEPENDENCY>
```

父子层级和依赖按需要使用，交付里程碑作为版本范围入口，不为简单任务强制新增父层级。建单前搜索已有任务，避免重复。平台写请求结果不明先回读确认、不盲目再建；完整处置见 [workflow.md](workflow.md) 的平台调用纪律。

## 2. 自动串行领取

队列范围必须来自本次文档对应的父 Issue 或里程碑，不能扫描全库就替用户领取任意任务。一个工作区一次一个叶子切片；优先恢复未阻塞活动切片；真实依赖阻塞时按串行让路流程保全并挂起，不并发执行。

1. 读取范围内开放 Issue 的原生字段、当前分支及开放 PR，识别在途任务。
2. 优先恢复当前作者唯一已指派的叶子任务；多个在途任务先报告冲突，不自行并发。恢复前确认其属于当前授权范围、原执行者退出、分支成果完整。
3. 否则选择未指派、没有子任务、没有开放 blocker 的叶子 Issue；就绪任务按 Issue 编号升序。读取详情确认验收标准可执行，遇到范围缺口先补清楚。
4. 指派给作者并设置 in-progress，回读确认，再从仓库默认分支用 issue develop 创建分支。指派是 GitHub 原生操作，不是分布式排他锁：此流水线要求一个串行调度者，不能宣称能抵挡并发抢占。
5. 无候选时区分：全部完成、依赖阻塞、被其他执行者领取、查询不完整。后几种报告原因；不能把空结果视为产品交付成功。

`ghship next` 是无副作用的确定性辅助，不做抢占、不创建任务；参数、分页与完整性保证见 [cli.md](cli.md)，查询范围及依赖语义由执行 agent 核实。

CLI 示例（参数替换为授权范围；超过 limit 必须分页继续，不把截断当完整）：

推荐直接用 `ghship next --milestone <实际里程碑编号> --json` 自动读取全部 Issue 及依赖页。调用方仍核对范围、在途标识、实际分支/PR 和领取前任务事实。父任务范围由 agent 递归读取。下方 stdin 方式用于已完整核实的小范围，可能截断或达到 1000 条时改用自动分页入口。

```bash
gh issue list --state open --milestone '<阶段>' --limit 1000 --json number,assignees,parent,blockedBy,subIssuesSummary | ghship next --author '<实际开发用户名>'
gh issue view <ISSUE> --json body,state,assignees,blockedBy,subIssuesSummary
TASK_REPO="$(ghship gh author -- repo view --json nameWithOwner --jq .nameWithOwner)"
ghship gh author -- api "repos/$TASK_REPO/pulls?state=open&per_page=100" --paginate --slurp
ghship gh author -- issue edit <ISSUE> --add-assignee '<实际开发用户名>' --add-label in-progress
```

只有父任务范围时，通过原生 subIssues 查询其叶子任务，递归覆盖嵌套子任务；blockedBy 列表若 totalCount 大于返回 nodes 数量必须补查。依赖关闭原因也要确认：not planned 的依赖并不自动代表所需能力已提供，应重新评估契约。

## 3. 单片循环

仓库变更：领取 → 实现与相关测试 → 作者提交 PR → 最新 CI → 作者退出并冻结源码 → 独立验收 → 返修或批准 → 原生门禁合并。

无仓库变更：按 Issue 标准执行研究、配置或人工验证；依据项目要求独立验收，结论写在 Issue，满足标准后关闭。需要独立验收时执行者先停止操作，由另一执行者复核；有仓库文件变更时走 PR 流程。

按 [workflow.md](workflow.md) 的命令及工作区、调用纪律执行。独立验收核对文档验收标准、源码、实际测试和风险，不用换凭据代替换执行者。返修仍在原 PR；作者/评审不同时修改同一工作区。合并自动完成子 Issue；本地维护失败先安全处置再使用工作区，不反转任务完成状态。

验证按改动与项目运行方式选择：结论依赖构建产物或工件时，核对其与实际源码、运行的对应关系；来源不可信或证据缺失时不能判为通过。本轮启动服务或依赖时，检查相关运行日志及其采集结果，结合项目约定判定预期错误和异常；进程成功不能代替日志结论。记录实际执行、日志检查和清理结果，失败或未知不得被其他步骤的成功掩盖；对外发布前核验权限并处理凭据及其他敏感信息。

测试结束前先保全必要证据，再回收归属明确的本轮临时资源。共享、未知归属及仍需恢复或审计的资源与证据保留并报告；发现资源不等于有权删除。清理失败或容量不足如实报告，不通过扩大删除范围换取通过。不涉及服务或临时资源的任务按实际情况执行，无需引入额外运行环境。

构建或依赖下载成本显著时，先测量实际时间、下载量与空间，再评估当前工具链原生的镜像、构建和依赖缓存。明确缓存作用范围、归属、容量、失效和冷启动路径，保留依赖完整性校验；不同执行环境不假定共享缓存。缓存不能替代本轮测试或证明产物来自当前源码；保留共享缓存与回收临时资源分别判断。

单片完成后重新读取队列和依赖，再领取下一片。流程错误不凭空建一串新 Issue；只有独立业务缺陷或需要追踪的修复才建单。自动化有停点：权限拒绝、测试失败无法解决、实质需求冲突、独有成果或活动写者冲突，报告具体信息，不能绕过。

## 4. 产品交付

子 Issue 全部关闭并不等于产品已验收。叶子任务合并后，按开发文档执行端到端验收（启动、关键业务流程、必要部署或构建产物），对照父 Issue 的覆盖表确认没有遗漏；运行证据、日志与资源收尾按上节适用原则核实。

如果发现组合后的问题，创建新修复 Issue/PR，关联产品父任务；不把已合切片都重开。产品验收通过后在父 Issue 留最终结果与产物入口，关闭父 Issue、必要时关闭 milestone，再向用户报告成果、验证和已知限制。无父任务的单片交付按其原验收标准完成。

产品级验收按明确的交付目标执行；部署和发布在用户授权范围内持续推进。

## 串行让路

当前片A被既有base缺陷阻塞时，保全提交并推送A、原PR置Draft、设A blocked-by修复B，执行者退出后解除A指派并移除 in-progress。工作区干净才切默认分支领取B。B合并后恢复A原分支/PR、指派和 in-progress、同步、测试及重新评审。不能安全保全则停止；不同时运行两个片。

## 最小在途标识

接入时确认原生 in-progress 标签存在，缺少时通过 `ghship gh dispatcher -- label create in-progress --description 'Currently being worked on' --color 1D76DB` 创建，已有则保留定义，未知写入先回读。恢复先查询本轮 Open 且带标识的 Issue，再核对 assignee、关联 PR 和分支；已指派但缺标签的任务也须检查，不能绕过既有成果。多个在途或事实不一致时报告并纠正，不自行并发。它不编码测试、验收或清理阶段，不增加多阶段 status/* 标签，不是权限、排他锁或合并门禁；合并由 GitHub 自动关单，标签尽力清理，清理失败不阻止原生关单、不重开 Issue。
